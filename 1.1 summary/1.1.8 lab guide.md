## Set up a record you can resume

Confirm the lab scope, network access, available time, and evidence requirements. Keep one note per system. Record the host, time, network position, and effective identity alongside any observation that changes your next decision. These details matter when the same check behaves differently after reconnecting or changing accounts.

For a lead you might revisit, write four short lines:

> **Observation:** The hostname resolves, but the connection closes before login.  
> **What it establishes:** Name resolution worked from this workstation.  
> **What remains uncertain:** The service, network path, and authentication state.  
> **Next check:** Determine whether the client reached the protocol handshake.

Record a check as **confirmed**, **inconclusive**, or **not applicable**. A missing tool or an access-denied response limits what you can establish. Keep the exact error with that observation.

## Turn discovery into a lead

Start with the services you can confirm. Record the protocol, port state, and where you observed each response. After pursuing the first useful lead, return to the full inventory. A quick pass may have skipped ports altogether, and an ambiguous UDP result may need an application response before you can identify the service. If two scans disagree, keep the target, protocol, and vantage point fixed while changing one setting.

A port number, banner, or advisory match is a starting point. Compare it with independent evidence such as an application response, build information, or a known local listener. If a service only responds from the host itself, record its bind address and which session could reach it. See [Stapler](../1.4%20capstone%20labs/1.4.104%20Stapler.md) for a service outside the default scan set and [Lampiao](../1.4%20capstone%20labs/1.4.520%20Lampiao.md) for a reproducible scan difference whose cause remained uncertain.

For a web lead, keep the request and response together. Record the method, path, authentication state, status, and redirect. Compare apparently identical sites by hostname and port before grouping them. If a response contains file data, ask what the application actually did with that data: return it, include it, or evaluate it as code. If submitted data is stored, establish which component later reads it and under which identity. [Geisha](../1.4%20capstone%20labs/1.4.513%20Geisha.md) shows similar landing pages exposing different paths. [Mailing](../1.7%20htb%20labs/1.7.209%20Mailing.md) shows why returning file contents and evaluating them support different findings.

## Diagnose the failure before retrying

Work out which stage failed before changing the tool or running the same check again.

| What you see | Useful next check | What would change your conclusion |
| --- | --- | --- |
| No connection or a connection closes early | Check reachability and which stage of the protocol was reached from the same workstation. | A completed handshake makes authentication or application behavior the next question. |
| A login appears to succeed inconsistently | Compare redirects, session state, and access to a page that requires authentication. | A successful request to a protected page is stronger evidence than a status code or cookie alone. |
| Login succeeds but access is denied | Identify the resource, the effective identity, and the exact permission that governs access. | The account can authenticate, but its access may differ by resource or session. |
| A session returns incomplete output | Check whether the connection and process are alive, then compare standard output and standard error. | A live process with unreliable output points to a session issue that needs separate confirmation. |
| A program fails to build, fails to load, or runs without a result | Record the exact stage and compare the build prerequisites, OS, architecture, and runtime. | A compiler error, loader error, and completed test with no relevant output support different conclusions. |
| Kerberos still fails after correcting the time | Verify the server name and service identity used by the client. Inspect tickets in the same logon session. | A consistent UTC clock removes one explanation. Name resolution and the requested service still need independent verification. |

[Jacko](../1.5%20pg%20labs/1.5.107%20Jacko.md) records unreliable Windows session output. [Sumo](../1.4%20capstone%20labs/1.4.514%20Sumo.md) separates a missing compiler component from a test that ran without effect. In [TheFrizz](../1.7%20htb%20labs/1.7.112%20TheFrizz%20%28Medium%29.md), correcting the clock exposed a separate hostname resolution problem.

## Reassess after a change of identity

Before interpreting a permission result, confirm the host, account, working directory, and session health. Repeat those checks after reconnecting or changing accounts. A different prompt is a cue to verify the context. Keep the last confirmed entry point in your notes so you know where to resume if the session drops.

On **Linux**, a file's owner, the ability to modify its contents, and the ability to replace its directory entry are separate facts. If a writable file looks significant, identify the process that uses it, the process's effective identity, and when it uses the file. A missing personal crontab leaves system schedules unexamined. A kernel version match needs corroboration from the distribution build and patch state.

On **Windows**, read group membership, token integrity, and privilege state separately. A privilege present in a token may be disabled. Distinguish a service's configured account from evidence that it actually ran, and check a scheduled task's principal separately from its state. If an ACL or task query is denied, record which identity ran the query.

In **Active Directory**, describe a permission as a relationship: **principal, permission, target, and scope**. Verify inheritance and effective access before treating a graph edge as confirmed. For certificates, evaluate enrollment rights, template configuration, and certificate mapping separately. With Group Policy, distinguish editing the policy from linking it. With LAPS or managed service accounts, identify who can read which objects or attributes. [Timelapse](../1.7%20htb%20labs/1.7.105%20Timelapse.md) illustrates why the scope of those rights matters.

## Know when to change direction

Give an uncertain lead a time limit. Before another attempt, state the result you expect and what you will conclude if you do not see it. Change one variable per attempt so a different result can tell you something.

When the time limit ends, write down the strongest evidence for the lead, what you tried, and what new evidence would justify reopening it. Then return to the full service inventory, reconsider an assumption about your current identity, or verify an artifact you previously set aside. If you use a write-up for help, read only far enough to identify the observation you missed, then return to your own notes.

## Close the lab with evidence

For each finding, save enough evidence to show the affected system, the effective identity where relevant, and the behavior you verified. Identify artifacts before opening them. Vaults, certificate bundles, memory dumps, directory backups, mail archives, and packet captures can contain sensitive data. Keep only the excerpt needed to support the result in a shareable report. Check that screenshots are legible and links open.

Write a short recap that answers four questions:

1. Which observation changed your next decision?
2. Which hypothesis did you rule out, and what evidence ruled it out?
3. What outcome did you verify, and what remained unresolved?
4. Which check would you reuse in another lab, and under what conditions?

Add verified command syntax and useful output fields to the [command reference](1.1.9%20command%20reference.md). Keep the decision that made the command useful in the recap.
