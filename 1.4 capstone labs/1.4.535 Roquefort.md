#### Recap
Gitea 1.7.5 ran on port 3000. Repository hooks could run basic commands, but the callback attempts did not establish an interactive shell. The separate repository configuration issue documented as CVE-2019-11229 yielded initial access.

Process monitoring showed root running the hourly cron jobs. The configured search path placed a directory writable by the current account ahead of the system location of run-parts. This exposed the scheduled task to search path hijacking and led to root access.
```bash
# /usr/local/bin/run-parts
chmod +s /bin/bash
```

Why did the repository configuration path and the hook path behave differently?
The two paths could execute commands in different contexts. Basic commands worked in the hook test, but I did not establish why the interactive connection failed.

Assess the hook process identity and its write permissions independently. A failed callback does not rule out other impacts from untrusted code execution.
