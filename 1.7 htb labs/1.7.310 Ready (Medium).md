Interaction between the two vulnerabilities
1. Redis supports a line-oriented inline command format. The protocol boundary became relevant when the importer passed untrusted data to an internal service.
2. Redis did not execute operating system commands directly. The security impact arose because it held the background job queue.
3. The GitLab worker evaluated data from that queue as Ruby code, converting queue integrity loss into remote code execution.

#### Recap

GitLab CE 11.4.7 exposed SSRF through project import and a CRLF injection flaw. Together they allowed access to Redis and undermined the integrity of GitLab's background job queue. The worker's handling of queued data led to code execution.

A GitLab configuration backup exposed the container's root password. Linux capabilities, writable cgroup controls, and host block device visibility showed that the container ran with extensive privileges.

The writable cgroup v1 release_agent crossed the container boundary and led to host-level execution.

The exposed host block device and mount capability also gave the container direct access to the host filesystem and the root flag.

Key Concepts:
1. Canonicalize address representations before applying SSRF restrictions.
2. Prevent untrusted input from crossing a line-oriented command boundary.
3. Protect Redis-backed work queues from untrusted writes.
4. Avoid privileged containers and restrict writable cgroup controls.
5. OverlayFS metadata can reveal host-backed storage paths.
6. Do not expose host block devices to application containers.
