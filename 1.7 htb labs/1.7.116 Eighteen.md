A conversion utility was available for Werkzeug's password hash representation.
```python:werkzeug_to_hashcat.py
import base64
import codecs
import re
import sys


if len(sys.argv) != 2:
    print(f'usage: {sys.argv[0]} <werkzeug hash file>')
    print('Input file has Werkzeug hashes one per line')
    sys.exit(1)

with open(sys.argv[1], 'r') as f:
    hashes = f.readlines()

for h in hashes:
    m = re.match(r'pbkdf2:sha256:(\d*)\$([^\$]*)\$(.*)', h)
    iterations =  m.group(1)
    salt = m.group(2)
    hashe = m.group(3)
    print(f"sha256:{iterations}:{base64.b64encode(salt.encode()).decode()}:{base64.b64encode(codecs.decode(hashe,'hex')).decode()}")
```

#### Recap
The initial SQL Server account could impersonate appdev and access the site's database. The database exposed a weak Werkzeug PBKDF2 password hash. The recovered password opened the site but yielded no further web findings. It was also reused by a domain account, which led to WinRM access and the user flag.

The Windows Server 2025 functional levels prompted a BadSuccessor assessment. Delegated object creation rights in the Staff OU exposed a dMSA migration path to domain administrator privileges. The resulting administrator access yielded the root flag.

Key Concepts:
1. Review delegated SQL Server impersonation rights and the databases accessible to the impersonated principal.
2. Identify how the application serializes PBKDF2-HMAC-SHA256 parameters before assessing password storage.
3. SQL Server can expose account names even when SMB is unavailable.
4. Audit OU object creation rights in Windows Server 2025 domains and verify remediation for CVE-2025-53779.
5. An isolated uv environment can keep one-off tool evaluations separate from system packages.
